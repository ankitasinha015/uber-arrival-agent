# Design: Uber Arrival Agent (Travel Mode x Eats)

Generated by /office-hours
Status: APPROVED
Mode: Builder (portfolio / interview artifact)

## Problem Statement

A traveler lands late at night (~11pm) in an unfamiliar city. The hotel kitchen is
closed. They are hungry, tired, and the status quo is: open Uber Eats in the car,
guess at what is open, guess at timing, hope the food and the human arrive at
roughly the same time. The painful parts of this are not the typing — they are
**surge/price uncertainty**, **no-show / supply risk**, and the **cognitive load**
of orchestrating it while exhausted.

## What Makes This Cool

An agent that owns the seam between **Travel Mode** (it knows your itinerary) and
**Eats** (it can order food). It does not wait to be asked. It watches the trip,
predicts when you will physically reach your hotel room, finds food that is actually
open, and continuously **re-times** the delivery as real events arrive (flight
landed, ride started, restaurant went offline). The interesting part is not the
chat — it is the agent choosing to **wait** because acting early would fail.

## Target User & Wedge

Late-night arriving travelers. Wedge = the single seam: **arrival-time -> food-timing**.
Not a platform. One agent, one seam, done well.

## Constraints

- Portfolio / interview artifact, not a production integration.
- Must demonstrate real agent engineering (tool-calling, event-driven re-timing,
  human-in-the-loop), not a conversational wrapper.
- "Rather than making it complicated" — minimal real dependencies.

## Premises (all agreed)

1. The pain is real but occasional. Acceptable for a portfolio piece — it demos
   *capability*, not retention.
2. The product is **not** autonomous pre-staging. It is **predict -> curate ->
   user authorizes payment**. The agent does all the work; the user taps once to
   authorize the spend. (Revised from an earlier "autonomous commit" framing after
   review.)
3. The product lives or dies on **timing prediction**, which is a stack of
   uncertainties (landing -> deplane -> customs -> bags -> ride -> check-in). The
   agent must **re-time continuously** as actuals arrive. This loop is the core.
4. It depends on Uber owning the trip context (Travel Mode owns the itinerary).
   For the demo this is an explicit assumption.
5. The demo must handle **no supply** gracefully ("nothing good is open near your
   hotel — want breakfast scheduled instead?").

## Approaches Considered

### Approach A: Scripted demo
Single-screen app, fake events on a timeline, LLM narrates. Fast, but nothing
underneath when the architecture is probed. Rejected — defeats the purpose.

### Approach B: Real agent loop (chosen)
Real tool-calling agent, event-driven re-timing loop, offline-restaurant recovery,
one-tap authorize step. Built on a framework-agnostic core with per-framework
adapters.

### Approach C: Re-timing simulator
Narrow mechanism demo — scrub flight delay, watch the agent re-decide. Good idea,
folded into B as the reasoning-transparency view rather than built standalone.

## Recommended Approach

**Approach B with a swappable core.**

- **Common core** (framework-agnostic): tool definitions, domain logic (re-timing
  calculator, recovery policy, delegation envelope), event model, agent-loop contract.
- **Primary adapter: LangGraph.** Best fit — the project is long-running,
  event-driven, stateful, human-in-the-loop. "Wait for ride-started then re-decide"
  maps to graph state + checkpoint; "user authorizes payment" maps to a native
  interrupt.
- **Contrast adapter: raw / Agent SDK.** Same agent, roll-your-own orchestration —
  an honest comparison of framework vs hand-built.
- **CrewAI / AutoGen: written evaluation only** (`docs/framework-comparison.md`).
  Their role/conversation-centric models do not fit an event-driven single-agent
  project. Building forced fits wastes time; the *analysis* of why they do not fit
  is itself the interview insight.

## Stack

LangGraph + Yelp Fusion API (restaurants + hours) + Maps API (ETA) + LLM.
**Flight status and order placement are mocked** — flight APIs are flaky and rate-
limited, and there is no public Uber Eats consumer API. The real external calls are
Yelp and Maps. No vector DB (Yelp category tags + a simple preference filter cover
taste matching; a vector DB would be complexity without payoff).

## Success Criteria

- The agent completes a full delayed-flight scenario end to end: predicts, curates,
  re-times at least twice, recovers from an offline restaurant, and produces a
  ready-to-authorize order.
- The same agent runs on both the LangGraph and raw adapters from one core.
- The reasoning at each re-time decision is visible (why it waited, why it acted).
